1. 结论与范围

结论：可行，但需要三层工作。NX2navi 的架构本身对非 NVIDIA 设备有明确降级路径（UMA 内存模式、非 NVIDIA gather bias、subgroup 32 降级、ASTC→BC3）， 代码里没有“只支持 NVIDIA”的硬门禁；真正的墙是 Intel 驱动在特定 Vulkan 用法上崩溃/极慢。因此移植的性质是 “驱动适配 + 特性降级 + 性能调优”，不是重写渲染器。

层级含义当前状态
T0 可运行能启动、过片头、进入场景、不崩溃已达成（规避模式 shadow=1）
T1 正确性画面/音画同步/着色器全部合法，无缺失渲染待验证（SPIR-V capability 缺口、VRS/mesh 路径）
T2 性能稳定 60 fps、启动不卡、预编译可控未达标（预编译 ~90 分钟，帧时间未测）

范围内：Arc B390（Xe3）核显 + Windows 11 + 驱动 101.9150；原生重编译路径（tools/make_game.py）。
范围外：DLSS / DLSS Frame Generation（需 RTX，改用 FSR 3.1）；其他 Intel 型号的保证；其他游戏。

5.1 M1 复测：import 不是充分条件，脏管线缓存才是共同项

第 2 节的第 1 行与第 6 行同时改了两个变量（缓存状态 + 内存模式），所以“import 必崩”这个结论一直没有被单独验证过。 M1 把两个变量拆开做了对照：缓存是干净的、而且已经被预热过（24,758 个翻译结果，来自一次完整的 --prepare-shaders）， 只把内存模式切到 import（NX2NAVI_MEMORY=import，不设 NX2NAVI_SHADOW）。

  • G3 才是主因侧：被中断的预编译留下的半写缓存会让 Intel 编译器在读管线时崩（同一偏移，读 0x190 是典型的空结构体字段）。8.4 的“临时文件 + 原子 rename + 启动头部校验”因此从体验问题升级为稳定性问题。
  • shadow 默认仍然是安全选择：它同时避开 import 通路（一旦该通路确实被触发）与外部指针的生命周期问题；代价是拷贝带宽，M1 的 mirror/verify/shadow 对照数据用来定这个代价。
  • 哨兵的价值不只在 import：任何“上次没正常退出”的情况（驱动崩溃、被强杀、断电）都会让下一次启动换到 shadow 并写回配置，避免用户在同一个崩溃里循环。
2026-11-10 15:30 更正：上面的“脏缓存是共同项”不成立。把三帧落到函数上以后，崩溃点是 vk_pipeline_save 里拷贝管线缓存的那次 vkGetPipelineCacheData，根因是它与建管线线程并发（驱动不自锁）， 见 5.4。缓存干净与否、import 还是 shadow，都只是改变“当时有没有在建管线 / 有没有触发保存”的旁观变量。

副作用提醒：现在这套 warm cache 就是“预编译跑完”的样子，make_game.py --until compile 不会去动它； 只有下一次完整构建（跑到 shaders 步）才会重写缓存——那一步必须在 M3 改成原子写之后才能安心中断。

5.2 M1 顺带抓到的一个真崩溃：RTSS 枚举把栈打穿了

跑内存模式矩阵时 mirror 与 verify 两次跑都在 8 分钟左右死掉，签名完全一样：

FATAL: access violation (0xc0000005) at host 00007FFAA183283D (ntdll.dll+0x1283d), writing address 0x5a9d76e0
  host frame  0: nx2navi+0x1086b50a
  host frame  1: nx2navi+0x109207fe
  not on a guest thread

exe 没有 DWARF，但有符号表，于是 nm -n 二分 + objdump -d 直接定位（RVA + 0x140000000）：

15086b4fa:  lea    0x40(%rsp),%rcx          ; char list[8192] 在栈上
15086b4ff:  mov    $0x2000,%edx             ; sizeof list
15086b504:  call   *enum_profiles           ; RTSSHooks64.dll!EnumProfiles(list, 8192)
15086b50a:  movb   $0x0,0x203f(%rsp)        ; <-- 崩在这里：list[8191]。rsp 已经被上一步打坏

崩溃点就在调用返回后的第一条指令：rsp 是坏的，说明 RTSS 的 EnumProfiles 写过了 8192 字节的缓冲区， 把保存的栈指针一起改写。位置是 rtss_limit.c: profile_exists()，跑在 RTSS 自己的 worker 线程上—— 和内存模式无关，之所以只在 mirror/verify 两轮出现，是因为它取决于 RTSS 何时注入接管（两次崩溃前一行都是 frame rate: RivaTuner Statistics Server has hooked the game）。

修法：把这份列表搬到堆上，并留 4 KB 全零余量——越界只能写进我们自己的余量，写不穿栈帧； 列表比 8192 字节还长时按 RTSS 自己报的 need 重新分配一次再读（日志会写一行 “read into a buffer of that size”）。 改动在 rtss_limit.c: profile_exists()（RTSS_LIST 8192 + RTSS_SLACK 4096）。 给用户的兜底开关本来就有：rtss = 0（NX2NAVI_RTSS=0）让 RTSS 完全不参与限帧。
复测状态：补丁已编入并在正常路径上验证（auto→shadow，40 s，60.1 fps，无 FATAL）； 但复测那一刻 RTSS 已经退出（日志 RivaTuner Statistics Server is installed but not running），崩溃路径没能在 RTSS 在场时再触发一次， 所以这一条记为“已修、待 RTSS 在场时确认”。

5.4 定案：崩溃发生在 vk_pipeline_save 里 vkGetPipelineCacheData 的拷贝上（2026-11-10 15:30，已修复并验证）

上面 5.1/5.3 只看到“同一驱动偏移”，此次把帧地址落到函数上才定案。方法：build-cache/ocarina.map 是链接器 的符号表（make_game.py 链接时写出，地址 = 映像内的偏移），崩溃报告里的 nx2navi+0x… 是 帧地址 - 模块基址，两者可以直接对齐（注意 .text 有 280 MB，objdump 对这么靠后的地址 不输出，要用脚本把文件切片再反汇编）。

igvk64.dll+0x79ddf3 读 0x190
nx2navi+0x108dcb0c  ->  vk_pipeline_save     + 0x40c  （0x108dc700 起，见 ocarina.map）
nx2navi+0x108dd2f5  ->  vk_pipeline_autosave + 0x125  （0x108dd1e0 起）
nx2navi+0x1092377e  ->  plat_thread_new/thread_main   （0x10923740 起；即 autosave_main）

三帧正好拼成 autosave_main → vk_pipeline_autosave → vk_pipeline_save → vkGetPipelineCacheData， 所以崩溃报告里的 “not on a guest thread”（非模拟线程）也解释得通：是自动保存线程。

把 ocarina.exe 在 0x108dcb0c 附近的字节切出来反汇编，可以看到返回地址正好落在 vk_pipeline_save 里第二次 vkGetPipelineCacheData(device, P.cache, &size, data) 之后那条指令上 （第一次只问大小，第二次才是把 100+ MB 拷出来）。5.3 那三次的 0x108dc55c / 0x108dcd45 也是同一对函数 （vk_pipeline_save / vk_pipeline_autosave），只是那次是另一版构建。

证据说明
15:18 那次是 mem: storage shadow (NX2NAVI_MEMORY=shadow)shadow 模式下照样崩在同一偏移 ⇒ 与 VK_EXT_external_memory_host 的 import 路径无关；5.1 的“脏缓存 + import”只在 import 那几次同时出现，是相关不是因果
全部 11 份日志都是同一偏移、同一 0x190不是随机内存踩踏，是驱动内部同一个空/坏指针字段（对象 + 0x190）
崩溃前一行多为 vk_pipeline_save 开头的 gpl 统计自动保存 20 s 一次，且只有“自上次保存以来新建过管线”才保存 ⇒ 播放中建管线（首段过场、大计算管线、GPL 链接）时才崩，纯播片不崩
清 shader-cache 后能跑缓存空了以后那些大变体不重建、当次运行没有新管线 ⇒ 没有保存 ⇒ 不触发；并不是“坏 SPIR-V”

根因：P.cache 被两拨线程同时用——后台/重放线程的 vkCreate{Graphics,Compute}Pipelines （带 P.cache）与 autosave 线程的 vkGetPipelineCacheData。代码里原本故意不加 VK_PIPELINE_CACHE_CREATE_EXTERNALLY_SYNCHRONIZED_BIT，把同步责任交给驱动；igvk64 101.9150 没做这件事， 拷出过程中缓存对象已被 worker 改动，于是在驱动内部解引用到 0x190。这是驱动 bug，但规避责任在我们。

修法（已编入，2026-11-10 15:58 验证通过）：vk_pipeline.c 新增 static PlatMutex cache_lock（SRW，读写锁语义）：

  • 缓存改为 VK_PIPELINE_CACHE_CREATE_EXTERNALLY_SYNCHRONIZED_BIT 创建；
  • 每次 pipe_create 带真缓存（非 VK_NULL_HANDLE）时取共享锁，见 pipe_create_cached()——构建线程之间仍完全并行；
  • vk_pipeline_save 的两次 vkGetPipelineCacheData 取独占锁（文件写仍在锁外，避免 20 s 一次的卡顿）；
  • vk_pipeline_shutdown 销毁缓存时也取独占。

开销：每次管线创建多一次 SRW 共享计数（相对几十 ms 的编译可忽略）；每次保存多一次独占（保存本身 ~60 ms）。

验证标准：跑一段“建管线 + 播放”混合的流程 ≥ 5 分钟，日志里出现多次 at a save of … MB 且没有 FATAL: access violation；pipeline-cache.bin 的 mtime 在运行中仍在更新。

验证结果（2026-11-10 15:53–15:58）：memory = import（以前每次必崩的通路）、ini 里不设 shadow，启动后跑过片头进入第一幕、总计 5 分钟以上：11 次 at a save of … MB（131.2 / 144.9 / 152.3 MB …），保存发生时构建线程正在建 547 条图形与 1024 条 compute 管线，FATAL 一条都没有；pipeline-cache.bin 由 111 MB 长到 159.6 MB，mtime 随每次保存更新。同一次运行的 stderr 里 igvk64+0x79ddf3 不再出现。附带确认（tools/find-calls.py 按符号反查 exe 的调用点）：编进产物的不只是保存侧的独占锁，pipe_create 里 3 处 plat_mutex_lock_shared 也在，所以构建线程之间仍然并行。本次帧率 35–52 fps 偏低，是因为运行前的预编译 --warm-shaders 被中断、运行时在补建管线，与锁无关。

8.4.2 XeSS 一直没生效的原因（2026-11-10 晚）

这是个真 bug，已修。vk_dlaa.c 的 vk_dlaa_frame() 每帧都重算 N.available， 而当时只有一句 FSR 3.1 的判定：

if (!N.ngx_up) N.available = fsr3() && cfg_bool("NX2NAVI_DLAA") && vk_ffx_load();

fsr3() 要求 taa = fsr3，所以 taa = xess 时每帧都把 N.available 覆盖成 0 → D.on = 0 → dl_active() 恒假 → XeSS 的上下文只在启动时打印一句“the temporal upscaler is Intel XeSS”，之后一次都没跑。 改成同时认 XeSS（vk_xess_load() && vk_xess_device_ready()，两者都是一次性静态结果，每帧调用无开销）后重建 （--until compile，16 s，不触发 shaders 步骤）。

修复后立刻暴露了第二层问题。日志第一次出现真正的 XeSS 调用：

xess: creating a context at 1440x810 -> 1920x1080 / xess: XeSS upscaling at 1440x810 -> 1920x1080 (quality setting 103) / dlaa: XeSS at 1440x810 -> 1920x1080，但紧接着是 dlaa: 1 frames anti-aliased (…; 1291 frames without the DLAA point, 0 with camera motion …)——1291 帧里只有 1 帧真的走到 DLAA 点。

顺带纠正一个前提：游戏内部渲染是 1440x810，输出 1920x1080（不是 1080p 渲染），所以超分本来有 0.75 的放大空间； 但 XeSS 的质量档 103 期望输入 1130x636，库自己也警告 “the library may reject it”。

当天的结论"超分和帧生成在 OOT 上都走不通"是错的，下一节把两条都推翻了。 framegen = off 只是第一层；vk_fg_wanted() 要求 dl_active()，所以要先把 DLAA 点打通。

8.4.3 打通 DLAA 点：XeSS 每帧真的跑了（2026-11-10 深夜）

上一节修好 N.available 后仍然 1 帧 / 1291 帧 miss，继续挖，发现是输出 pass 被比例判据筛掉：

int big = D.share_off || share <= 0 || share >= 1 || c->width >= 0.95 * D.color.width / share;

share 来自 wide_dlss_share()，即菜单里 DLSS 档位（quality = 2/3）。OOT 没有场景/输出补丁集， 渲染分辨率是游戏自己定的（实测 1707x960 或 1920x1080），永远不会等于 2560×0.667 = 1707 之外的值， 于是 1920 宽的 pass 被要求 ≥ 2050 才认，每帧都被判成"不是输出 pass"。 修法是：res_sizes() 给的是占位值时（res_adjustable() == 0），任何比场景大的单色无深度 pass 就是输出 pass。

修复后日志第一次出现持续运行：

xess: XeSS upscaling at 1707x960 -> 2560x1440 (quality setting 104) / dlaa: 300 frames anti-aliased (…; 298 with camera motion, 298 with the characters' mask …)—— 前 1104 帧 miss 是因为启动画面渲染 1920x1080（不按 2/3 比例），进游戏后场景变成 1707x960 才开始命中。

代价与收益都取决于输出尺寸，实测两组：

输出场景 → 输出帧率1% low>25 ms
2560x14401707x960 → 2560x144040.2 fps13.2751
1920x1080960x540 → 1920x108054.0 fps32.390

同一台机器、同一存档：输出从 1440p 降到 1080p 就多了 14 fps，比任何超分设置都管用。 游戏内部渲染尺寸随输出自己变（1080p 输出时只渲染 960x540，正好是 XeSS 的 2× 档）， 所以这时 XeSS 是白赚的——原来的 2× 暴力放大换成了重建放大，画面更实，帧数不掉。

顺带纠正输出分辨率：window_size 不是最终输出尺寸，fullscreen = 1 时按显示器走（曾见到 2560x1440）； 改 fullscreen = 0 用窗口模式跑会直接异常退出（0xC000013A），这条路暂时不通。

帧生成：通了（根因是队列族，不是扩展）

先修掉一处接线缺失：vk_device.c 只在 nq_gfx >= 2 时调用 vk_fg_queues()， 只申请一个图形队列的设备上 F.present 恒为空，vk_fg_create_swapchain 直接返回 FEATURE_NOT_PRESENT， 日志里连一个 fg: 字都没有。补上后能发起创建，但 FFX 一直拒绝：

fg: the frame generation swapchain failed (3): frame generation off for this run（3 = FFX runtime error）。

先按常规思路补了 VK_KHR_present_id / VK_KHR_present_wait——驱动根本不提供，both 0， 可见它不是硬条件。真正的原因是把队列族打印出来之后才看见的：

族flags队列数可呈现
00xf（图形+计算+传输+稀疏）1是
10xa（计算+稀疏）4是
20xc（传输+稀疏）2是

Intel 的图形族只给 1 个队列，而 AMD 的帧生成必须在一个和游戏队列不同的、能 present 的队列上跑。 一直拿不到就返回 runtime error。改成从 family 1（4 个队列、可 present、计算能力足够跑插值）取三个队列 ——present 0、acquire 1、async compute 2——并把交换链改成跨族 VK_SHARING_MODE_CONCURRENT（族 0 + 族 1）， FFX 立刻接受：

fg: AMD FSR 3.1 frame generation swapchain, 1920x1200 / fg: frame generation context for 1920x1200, render size up to 1920x1200

注意 VK_QUEUE_COMPUTE_BIT 隐含传输能力，family 1 的 flags 里没有 TRANSFER，按位要求它反而挑不到这个族。

实测：屏幕 60 fps，游戏内部 37.8

60 秒窗口：

frametime: 60 s: 2269 frames in 60.0 s, mean 37.8 fps, 1% low 19.5 fps, over 25 ms 692 / fg: 3600 frames presented, 1592 generated (1593 with the HUD kept out); paused 445 (menu), 1562 without depth and motion

呈现 3600 帧 / 60 s = 60 fps，其中 1592 帧是插出来的。另有 1562 帧因为“没有深度和运动矢量”被跳过，主要是菜单/切场景。

XeSS 与插帧可以同时开：dlaa: 300 frames anti-aliased (scene 960x540, output 1920x1080 … 298 with camera motion)。

试玩反馈的两个毛病：鬼影、抖动

鬼影查到一处硬伤：喂给 FSR 3 的相机 FOV 是写死的 1.0f 弧度（57.3°），而游戏实际画的是 50.0°～52.8°（从投影矩阵 P[5] 反解，vk_dlaa.c c->fov_y）。内参偏 8%，深度重投影就会错位， 移动边缘被拖出残影。改成读真实值：

fg: camera known, vertical fov 0.922 rad (52.8 deg) → 0.873 rad (50.0 deg)

抖动的根源不在插帧算法，而在呈现模式。这台机器是 144 Hz 屏，配置写 vk_present = mailbox， 但日志是：

gfx: present mode immediate (NX2NAVI_VK_PRESENT=mailbox)

Intel 驱动既不给 mailbox 也不给 fifo_relaxed，pick_present_mode 一路退到 IMMEDIATE——完全不等 vsync。 插帧输出 ~99 fps 对着 144 Hz 自由翻转，节拍随机落在刷新边界上，观感就是一顿一顿。改成 vk_present = fifo 后：

FIFO 不但治抖动，内部帧率还从 49.7 升到 61.8——呈现阻塞把 GPU 的压力摊平了。 反直觉的一条：限帧加插帧会互相打架，限到 36 想让 2×36=72 对齐 144，结果内部掉到 25、50 ms 以上 1331 帧， 比不限帧还糟（限帧器的 sleep 与 present 的阻塞叠加成恶性循环）。

手段实现位置本机结果

9. XeSS 与帧生成（新增需求）

结论：XeSS 超分（XeSS-SR）可以做，XeSS 帧生成（XeSS-FG）在 Vulkan 渲染器里做不了。 Intel 官方文档与 SDK 的接口约定是：XeSS-SR 提供 Vulkan 入口（xessVKCreateContext / xessVKGetRequiredDeviceFeatures / xessVKExecute / xessVKBuildPipelines）， 而 XeSS-FG 与 XeLL 仅有 DirectX 12 实现，且二者必须同时开启。本项目是纯 Vulkan，所以帧生成沿用已有的 framegen = fsr3（FFX API on Vulkan，任意 GPU），XeSS-FG 不接入。

能力官方支持本项目（纯 Vulkan）能否接入结论
XeSS-SR 超分DX11 / DX12 / Vulkan（SDK 3.x，Xe3 走 XMX 全质量档）可以：与现有 NGX 路径同构，只是换库换入口做
XeSS-FG 帧生成仅 DX12（XeSS 2.1 起支持第三方 SM6.4 卡，但仍限 DX12）不可：需另建 D3D12 设备 + Vulkan↔D3D12 外部内存互操作 + DX12 swapchain 归属不做
XeLL 低延迟仅 DX12，且必须与 XeSS-FG 同开不可（同上）不做
XeSS-MFG 多帧生成XeSS 3，仅 DX12不可不做
帧生成替代AMD FSR 3.1 FG，FFX API 原生 Vulkan项目已实现（vk_fg.cpp + amd_fidelityfx_vk.dll）用这个
图 4　超分后端抽象：帧逻辑不变，新增第三个后端（XeSS-SR）即可；帧生成走 FSR 3.1

9.3 XeSS 选项从菜单里消失（2026-11-10 晚，已修）

用户反馈：ini 里 taa = fsr3 之后，游戏内菜单再也找不到 XeSS 的档位。查到是自锁逻辑：

menu.cpp:829 const bool xess = vk_dlaa_xess_available(); → vk_dlaa.c:131 return vk_xess_loaded(); → vk_xess.cpp:297 return A.ok;

而 A.ok 只有 vk_xess_load() 成功后才置位，vk_xess_load() 又只在 vk_dlaa_init() 里、且 ini 写着 taa = xess 启动时才会被调用（vk_dlaa.c:255）。于是：

选了 FSR 3.1 → libxess.dll 从不加载 → A.ok = 0 → 菜单判定 XeSS 不可用 → 不列出 → 没有入口切回去。

修复：新增 vk_xess_present()（vk_xess.cpp），只用 GetFileAttributesA 查 exe 同目录 libxess.dll 是否存在，不加载库、不碰设备；vk_dlaa_xess_available() 改用它。 菜单要问的是“这台机器能不能提供 XeSS”，不是“这次运行有没有加载过它”。
